# oosync Architecture Guide

This is the top-level architecture guide for the oosync repository.

oosync is a schema-agnostic offline sync toolkit. It has three major responsibilities:

1. Introspect a Postgres schema and generate consumer-owned sync artifacts.
2. Provide a portable sync runtime that moves data between a local SQLite database and a remote worker.
3. Provide a generic worker runtime that applies sync policy against Postgres using injected artifacts.

The repository is intentionally consumer-agnostic. Application-specific behavior belongs in generator inputs, configuration, or consumer wiring, not in oosync runtime code.

## Repo Topology

- `src/codegen-schema.ts`
  - Postgres introspection and artifact generation.
- `src/shared/**`
  - Shared protocol types and portable metadata helpers.
- `src/runtime/**`
  - Platform/runtime abstractions used by the sync engine.
- `src/runtime/browser-sqlite.ts`
  - Generic browser sql.js runtime for WASM bootstrapping, IndexedDB persistence, migration execution, trigger installation, outbox backup, and sync runtime wiring helpers.
- `src/sync/**`
  - Core sync runtime: outbox handling, push/pull orchestration, adapters, remote-change application, realtime integration, and service lifecycle.
- `worker/src/index.ts`
  - Generic worker factory and request handling.
- `worker/src/sync-schema.ts`
  - Config-driven schema helpers for worker filtering, sanitization, and rule evaluation.
- `worker/src/debug.ts`
  - Worker diagnostics helpers.

## Mental Model

Use this model when reasoning about changes:

1. Postgres is the remote authoritative schema.
2. `src/codegen-schema.ts` inspects that schema and derives sync facts.
3. oosync writes generated outputs into consumer-owned paths.
4. The consumer app runs against local SQLite and queues local writes.
5. The oosync runtime pushes queued changes to a worker and pulls remote changes back.
6. The worker uses generated schema/config artifacts to apply sync logic against Postgres.

The live runtime source of truth for the consumer is local SQLite. oosync is the transport, normalization, and reconciliation layer around that database.

## Generated vs Hand-Written

Generated outputs are part of the contract, but they are not owned by this repository at runtime.

Generated by `src/codegen-schema.ts` into consumer-owned paths:

- SQLite Drizzle schema
- optional SQLite schema wrapper that adds the sync outbox table
- optional browser SQLite client wrapper
- shared/generated table metadata
- consumer-facing table metadata projection
- optional sync runtime-config wrapper that injects the browser SQLite runtime
- worker Postgres schema
- worker config
- optional worker entrypoint scaffold
- optional SQLite migration support files when configured

Hand-written code that remains in this repository:

- the code generator
- shared protocol definitions
- runtime interfaces and portable helpers
- sync engine, outbox, adapters, and service lifecycle
- generic worker runtime and rule interpreter

Rule: do not hand-edit generated consumer outputs to fix behavior. Fix the generator, the Postgres schema, table comments, or config inputs instead.

## Artifact Flow

Artifact flow is how schema facts become runtime contract:

1. A consumer defines or changes remote Postgres schema.
2. The consumer runs `npm run codegen:schema` or invokes `src/codegen-schema.ts` directly.
3. oosync introspects catalogs, constraints, column types, foreign keys, indexes, and table comments.
4. oosync merges inferred facts with consumer overrides from `oosync.codegen.config.json`.
5. oosync writes generated artifacts into consumer-owned output paths.
6. The consumer app and consumer worker import those outputs.

The key architectural point is that schema agreement is generated, not maintained manually in multiple places.

When configured, codegen can also emit thin browser wrapper files so consumers keep only app-specific hooks and config by hand instead of duplicating sql.js bootstrap and runtime-wiring boilerplate.

## Runtime Flow

Runtime flow is how data moves after a user changes local state:

1. A consumer writes to local SQLite immediately.
2. Local triggers or queue logic append changes to the outbox.
3. `SyncService` and `SyncEngine` package pending changes and request remote updates.
4. The worker authenticates the request, applies push logic to Postgres, evaluates pull rules, and returns normalized changes.
5. The sync runtime applies remote changes back into local SQLite while suppressing local-trigger feedback loops. For rows with sync timestamps, updates and deletes compare modification times within the SQLite write so an older response cannot overwrite a newer local edit. Equal timestamps allow server normalization; tables without timestamps retain unconditional application.
6. The consumer continues to read local SQLite; it does not switch to direct remote reads after sync.

Default conflict handling is last-write-wins unless the consumer layers additional conflict behavior above the shared protocol.

Worker upserts first use the configured unique key in a savepoint. PostgreSQL
therefore determines conflicts using actual defaults, trigger effects, and the
constraint's NULL-distinctness semantics. Only a primary-key violation verified
against the live catalog (relation, constraint, and primary-key columns, following
partition-parent constraints when applicable) permits
an identity fallback after rollback of the failed attempt. Unrelated constraint
failures, including nested PL/pgSQL trigger errors identified by PostgreSQL execution context, propagate unchanged. The fallback compares every natural-key component
to the proposed insert with `IS NOT DISTINCT FROM`; a mismatch rejects the write.
This prevents reassignment across natural-key boundaries, including ownership
components, but does not replace caller authorization. Natural-key components are
immutable through this sync upsert path, including NULL-to-value placeholder
completion, value-to-value edits, and value-to-NULL edits. This batch enables
repeat uploads with the same natural key; it does not enable natural-key edits.
Supporting those edits needs a separate consumer-defined authorization policy.
On identity fallback, an empty RETURNING result cannot distinguish guard rejection
from a skipping trigger, so the diagnostic lists both possibilities without
asserting a cause. On the natural-key path, it directs attention to skipping triggers.

Known follow-up: a rejected natural-key edit aborts the push batch, and the retained
outbox item can repeatedly block later uploads. This predates the fallback fix.
Per-row rejection/quarantine needs a separate protocol and recovery design that
preserves rejected local work and does not acknowledge unapplied writes.

All uploads, including minimal-payload retries, must retain every primary-key
component. Configured minimal-payload retries automatically retain both primary-key and natural-key components from the original payload. Database-generated identities are not a substitute for a stable sync
identity. Empty or undefined-only update sets are rejected with configuration
diagnostics. Updated natural-key properties use trigger-normalized `excluded`
values, matching the fallback guard. Configured insert-only properties remain
excluded from updates. A write returning no row is rejected rather than silently
acknowledged; conflict conditions and skipping triggers can both cause this.
The fallback has its own savepoint, checks the existing row identity before updating, and verifies every returned primary-key component against the upload identity. A trigger that changes identity on retry
therefore causes rollback rather than silently inserting a different row.

The configured unique arbiter must be usable by PostgreSQL's `ON CONFLICT`.
Identity fallback additionally requires a non-deferrable primary-key arbiter.
A deferrable primary key does not block successful natural-key inserts/updates,
but an immediately checked duplicate requiring identity fallback gets an explicit
unsupported-schema error without changing the stored row. Initially deferred
violations are reported by PostgreSQL at outer transaction commit; the Worker
must await that commit before acknowledging uploads. The helper cannot catch
commit-time violations. No indexes or constraints are installed
implicitly. A target table literally named `excluded` is unsupported because it conflicts with PostgreSQL's proposed-row namespace; the helper rejects it before executing SQL.

Catalog lookup follows the same schema/search_path resolution as the INSERT.
An unqualified table must not be forced to public only for catalog verification.
Constraint results are intentionally not cached across requests: schema changes
and session relation resolution could invalidate an isolate-wide cache. Measure
batch latency before introducing a cache with a defined invalidation strategy.

Each attempt locks an existing upload identity before inserting, and verifies the returned identity and natural key against that snapshot. This prevents a natural-key collision from silently updating a different existing identity and rejects BEFORE UPDATE key mutations. New identities may still deduplicate by natural key as configured. The lock adds one SELECT per attempt; batch latency across a deployed database connection remains to be measured. A row absent at the attempt may be inserted, including after a concurrent hard delete; this helper does not provide tombstone protection.

Each attempt uses a driver savepoint inside an explicitly released boundary, so large batches do not retain one savepoint per row. The driver scope is required to isolate its failed-query tracking. Failure cleanup restores and releases the enclosing boundary; if cleanup also fails, an AggregateError retains both errors and stops retrying the unusable transaction. The normal path adds savepoint commands; only a primary-key-conflict retry
adds a catalog query and another insert attempt. Transactional effects from the
failed attempt roll back; PostgreSQL sequence consumption need not roll back.

In lenient codegen, the PostgreSQL worker schema preserves otherwise unsupported
database default expressions as SQL defaults. SQLite default translation and
strict-mode validation are unchanged; consumers regenerate worker artifacts to
pick up this metadata. Conflict selection does not infer default values from
that metadata.

## Key Boundaries

### 1. Codegen Boundary

- `src/codegen-schema.ts` is the source of truth for generated artifacts.
- Generated outputs are consumer-owned and write-only.
- Codegen should prefer inference from Postgres catalogs and comments before requiring manual overrides.

### 2. Shared Contract Boundary

- `src/shared/**` must remain portable and data-oriented.
- Protocol types should not import consumer code or worker-specific runtime state.
- Shared metadata is contract, not application logic.

### 3. Library Runtime Boundary

- `src/**` must remain independent of `worker/**`.
- The sync runtime depends on injected runtime/platform hooks rather than browser-framework or worker-specific globals.
- Consumer-specific notification, storage, auth wiring, view setup, compatibility tables, and schema objects should enter through configuration or runtime injection.
- `src/runtime/browser-sqlite.ts` may own reusable browser-local database lifecycle behavior, but it must stay schema-agnostic and accept consumer specifics only through generated metadata and injected hooks.

### 4. Worker Boundary

- `worker/**` owns generic request handling, auth validation, Postgres access, push application, and pull evaluation.
- The worker must receive schema tables, syncable table names, metadata, and worker config from injected artifacts.
- Worker logic must not hard-code consumer schema assumptions.

### 5. Consumer Boundary

- Consumer-specific table names, ownership rules, collections, and domain semantics belong in config, generated artifacts, or consumer code.
- If a behavior is only correct for one application, it does not belong in oosync runtime code.

## Configuration Inputs

oosync primarily learns about a schema from these inputs, in this order:

1. Postgres catalogs and constraints
2. Postgres table comments with `@oosync.*` tags
3. `oosync.codegen.config.json`

Use overrides to express exceptions, not as the default modeling mechanism.

### Library Runtime

  - Sync lifecycle, scheduling, realtime coordination, and consumer-facing control surface.
- `src/sync/realtime.ts`
  - Optional realtime integration that triggers pull work.
- `src/sync/runtime-context.ts`
  - Injected runtime dependencies such as local schema, queue table, sqlite instance access, persistence hooks, and logging.

### Sync shutdown

`SyncService.stopAutoSync()` pauses scheduling and cancels startup retry waits
and deferred online listeners; it can be restarted. It does not drain requests
already running. `await service.destroy()` is the permanent, idempotent shutdown
boundary: new sync/start calls are rejected, Realtime subscriptions and debounce
callbacks stop, and active service DB operations (including periodic outbox
probes and persistence) drain before it resolves. Consumers must await it before
closing or replacing SQLite. Requests already running finish normally rather
than being abandoned during apply/persistence. Consumer-owned async completion
callbacks still require consumer lifetime guards. Failed subscription teardown
can be retried by calling `destroy()` again; the service remains closed to new
sync work during that retry. No schema or worker protocol
change is involved.

### Browser database rebuild safety

Before a database-version rebuild, schema-version clearing, or configured forced-reset URL, the browser runtime inspects the persisted database through an isolated, read-only SQLite snapshot. Any remaining `sync_push_queue` row blocks the operation regardless of status. Nonempty, unsupported, or unreadable persisted outbox backups also block it. Inspection failures fail closed. A blocked initialization leaves database bytes, version, backup, and sync watermark intact and throws `BrowserSqliteMigrationBlockedError` with a `reason` of `outbox`, `backup`, `local_data`, or `inspection_failed`.

Every populated application table blocks by default, including tables present in the new `syncableTables` contract. New metadata and installed triggers do not prove that pre-existing rows reached the server. Promoting a previously local-only table to synced status is supported only after its rows are durably preserved and approved through the hook; membership in the new sync schema never authorizes discard. SQLite internals and runtime trigger-control metadata are excluded. Consumers may provide `hooks.canDiscardLocalTable({ rawDb, userId, tableName })`, returning exactly `true` only for reconstructible data or data already durably preserved. The hook receives the read-only snapshot; it cannot waive outbox or backup checks. No consumer table names are built into the guard. Wire this through consumer-owned hooks, not edits to generated wrappers.

The guard detects risk; it does not synchronize an old schema, export local-only data, or replay incompatible writes. Recover using a compatible app to synchronize or preserve local work before retrying. Consumers should display the blocked error and must not respond by clearing storage. Normal startup without a migration remains available with pending writes. Explicit `clearDb()` is still a destructive consumer operation and is outside this guard.

This is a persisted-snapshot check, not cross-tab locking or proof that every synced row exists remotely. It assumes the outbox contract correctly tracks local writes. Coordinate shutdown of old tabs/devices and persistence of in-memory changes before upgrading; concurrent writers remain a separate lifecycle concern.

## Change Workflows

### Schema / Codegen Change

1. Adjust Postgres schema, comment tags, or expected inference behavior.
2. Update `src/codegen-schema.ts` if inference or output generation must change.
3. Regenerate artifacts in the consumer project, including thin browser wrappers when `browserSqlite` outputs are configured.
4. Run the drift check path.
5. Validate that runtime code still matches the generated contract assumptions.

### Sync Runtime Change

1. Identify whether the change belongs in shared contract, runtime context, engine behavior, or worker behavior.
2. Preserve the separation between `src/**` and `worker/**`.
3. Validate the smallest relevant commands and tests.

## Guidance For AI Agents

When changing this repository, first decide which layer owns the work:

- Generator/input modeling issue: start with `src/codegen-schema.ts`.
- Shared protocol or metadata issue: start with `src/shared/**`.
- Local sync runtime issue: start with `src/sync/**` and `src/runtime/**`.
- Worker-side push/pull behavior issue: start with `worker/src/**`.

Do not solve consumer-specific problems by hard-coding consumer logic into oosync. The durable architecture is: schema and config as inputs, generated artifacts as contract, local SQLite as the consumer runtime source of truth, and oosync as the generic sync engine and worker implementation.
